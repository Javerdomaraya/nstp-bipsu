# Coordinator Hardening — Final Implementation and Verification Report

BiPSU NSTP system · 23 August 2026

This report closes out the Section 7 remainder of `COORDINATOR_INTEGRATION_REPORT.md`. The seven remaining priorities were implemented rather than re-audited, the repository-wide security search was carried out with every occurrence classified, the twenty required regression tests were written and executed, and the coordinator surface was traced end to end for CWTS, LTS, MTS and for an intentionally unassigned coordinator. Every claim below is backed either by an executed test or by a cited line of source; where a test could not run in this Linux sandbox that is stated explicitly and counted separately, never as a pass.

## 1. Problems fixed, with root causes

**Invalid component values were coerced to CWTS (P1).** Student imports and the admin roster forms accepted any string in the component column and fell back to `'CWTS'` when parsing failed. The root cause was that the component vocabulary had no validator — the label was cast to `NstpComponent` at each point of use, so a misspelling like `CWT`, a blank cell, or a stale spelling such as `MTS (Air Force)` became a real CWTS enrolment, and a student ended up in a program nobody assigned them to. The fix introduces `toNstpComponent` in a dependency-free module (`frontend/src/data/nstpComponents.ts`) that accepts only the canonical five names, and `validateStudentImportRows` (`frontend/src/utils/studentImport.ts`), which validates the whole batch before anything is written and reports each bad row by number and email. A batch containing one invalid row now imports nothing at all, so no partially created student can carry an inferred component. Legitimate aliases the application already supported — case and whitespace variants, `MTS (NAVY)` — still resolve.

**The module query had a latent fail-open (P2).** `resolveModuleComponent` (`backend/src/modules/nstp/nstp.service.js:159`) tested `Array.isArray(scope) && scope.length` before refusing a component-less write. An empty authorised component list therefore skipped both guards and fell through to an unscoped write. In practice it was unreachable, because a coordinator with no components is rejected upstream in `getCurrentCoordinator`, but it was a fail-open spelling of the invariant sitting one refactor away from being reachable, and it disagreed with `outsideForcedScope` (`:193`), which already read `[]` correctly. The function now normalises the string form to a one-element array so the two shapes cannot drift, and treats presence alone as a narrowing: only `null` and `undefined` — reachable exclusively from the admin controllers, which pass no third argument — mean unrestricted. Four new tests cover create, update and delete under an empty allow-list.

**Coordinators wrote into shared admin snapshot storage (P3).** `ensureNstpSeedData` ran on boot for every role and seeded seven empty collections into the shared snapshot keys, and several coordinator screens replaced those keys with their own component-scoped subsets. Because the admin screens, the shell counters and `RoleDashboardHome` read those keys as though they were global, a coordinator's partial view could be presented to the next session on the same tab as the whole institution. The seeding now returns early for a coordinator session (`frontend/src/data/nstpData.ts`), which is invisible to readers since an absent key and a key holding `'[]'` both parse to `[]`; `CoordinatorDashboard` touches no snapshot function at all; and `ModulesPage` / `AssessmentsPage` route their writes through a single `applyModules`-style helper that skips the snapshot whenever the list is component-scoped. Logout cleanup and the boot-time `clearSessionSnapshots()` remain, but as defence in depth rather than as the architecture — nothing now depends on them running.

**ReportsPage loaded admin snapshots on the coordinator path (P4).** The page called `loadStudents()`, `loadModules()`, `loadAssessments()`, `loadAccounts()` and `loadTrainingGroups()` unconditionally and then narrowed the results per role, which meant a coordinator's execution read global data it was not entitled to before discarding most of it. Every one of those loaders is now confined to a single helper, `loadSnapshotReportSource()`, called from exactly one place — the `else` arm of one explicit fork, `isCoordinator ? coordinatorData : loadSnapshotReportSource()`. The guarantee is now a property of the control flow rather than of the filtering that follows it, and the regression test asserts each loader appears exactly once and only inside that helper.

**Coordinator training groups were fetched globally and filtered in React (P5).** The reports screen had no scoped source for training groups, so the coordinator branch either omitted them or read the shared snapshot. A scoped endpoint now exists — `GET /api/nstp/coordinators/component/training-groups`, guarded by `getCurrentCoordinator`, implemented by `listCoordinatorTrainingGroups` (`nstp.service.js:334`), which throws if it is handed anything other than an array of authorised component ids and restricts the rows inside the database query. The client (`frontend/src/services/coordinator.ts`) performs no filtering of its own; the only `.filter` in that file is `.filter(Boolean)` on a JSON column inside a single row, which cannot select records.

**Authenticated-user typing was permissive (P6).** The session object was an untyped bag with an index signature, so reading enrolment flags off a coordinator or a scope off a student compiled cleanly and produced `undefined` at runtime — which is how staff accounts were routed into the student enrolment funnel. `frontend/src/services/authUser.ts` now exports a discriminated union on `role` with per-variant fields, and `normalizeAuthenticatedUser` fails closed: a payload whose role it cannot classify returns `null` rather than defaulting to the student workspace. Credentials and the raw unvalidated `coordinatorScope` key are stripped at every level that gets spread into the result, including inside `User.data`. No `any` was traded for a suppression; `npx tsc --noEmit` exits 0.

**Scope mapping was duplicated and could drift (P7).** `COORDINATOR_SCOPE_TYPES` existed in the backend staff service and was re-declared in the request middleware, and the frontend held its own copy of both the scope list and the scope→component map. The backend copies were collapsed to one import, so `nstp.authorization.js` and `staff.service.js` can no longer disagree about which components a program owns. The frontend copy was deliberately *not* merged into a shared file — that would compromise the separation the directive protects — but it is now documented as display-only metadata, with the backend named as the sole authorization authority, and `backend/test/scope-mapping-drift.test.js` asserts the two stay in step. Both the frontend scope vocabulary and its validator now have exactly one implementation, in the dependency-free leaf, re-exported from the two modules the rest of the client expects to import them from.

Two further coordinator-facing defects surfaced during the final trace and were fixed in the same pass. **Coordinator module creation was a guaranteed 403.** The shared `ModulesPage` editor had no component field, `createEmptyModule()` produces `component: 'Common'`, and the API correctly refuses a component-less write from any narrowed actor — so a coordinator could fill in the form, save, and receive an opaque authorization error with nothing to correct. The editor now seeds a new draft with the coordinator's first in-scope component (matching `CoordinatorDashboard.tsx:179`), exposes a picker limited to the components the scope hook reports, and refuses to submit a component-less draft with an instruction instead of letting it become a 403. This is presentation only: the options come from display metadata and the server re-derives the real scope on every save. **The PDF export dropped a coordinator's own training groups.** The PDF branch still gated that table on `user.role === 'admin'`, a leftover from before the scoped endpoint existed, while the on-screen table and the XLSX sheet already included the rows — so the same report disagreed with itself. The gate now matches the other two, and the stale comment that justified it is gone.

## 2. Files changed, and what each is responsible for

On the backend, `nstp.service.js` holds the authorization-relevant query construction: `resolveModuleComponent` and `outsideForcedScope` decide which component a write may attach to, `moduleAccessFilter` (`:249`) distinguishes "no rows reachable" (`null`) from "no restriction" (`{}`), the assessment filter at `:494` narrows a coordinator to `componentId: { in: actor.componentIds || [] }`, and `listCoordinatorTrainingGroups` (`:334`) is the new scoped read. `nstp.authorization.js` is the single place coordinator scope is derived from the database per request; its legacy single-component branch now reports `allowedComponentTypes: null` rather than an empty array, so no consumer can mistake absence for permission. `staff.service.js` owns `COORDINATOR_SCOPE_TYPES` and `requireAllowedComponent` (`:104`), which is what stops a coordinator creating or re-pointing a facilitator outside its program — applied on both create (`:207`) and update (`:229`) on top of the ownership filter (`:198`). `grades.service.js` overwrites any client-supplied `componentId` with `undefined` and substitutes the server-derived list (`:258`). `nstp.controller.js` exposes the three scoped coordinator reads at `:373`, `:392` and `:412`.

On the frontend, `data/nstpComponents.ts` is new and deliberately dependency-free: it holds the component vocabulary, the coordinator scope vocabulary, and the two validators, so security-critical parsing can be imported — and executed under a plain Node runner — without pulling in the API client. `utils/studentImport.ts` is the batch validator. `services/authUser.ts` is the canonical session shape and normaliser, and is now runtime-dependency-free for the same reason. `services/coordinator.ts` and `hooks/useCoordinatorScope.ts` are the coordinator read surface and its display metadata. `data/nstpData.ts` owns the snapshot store and no longer seeds it for coordinators. `pages/ReportsPage.tsx` has one fork between coordinator endpoints and snapshot sources; `pages/ModulesPage.tsx` and `pages/AssessmentsPage.tsx` keep component-scoped lists out of the shared snapshot and, as of this pass, let a coordinator name a component; `features/coordinator/pages/CoordinatorDashboard.tsx` reads only scoped endpoints; `App.tsx` normalises the session once and clears both caches on boot and on logout.

Test files added: `backend/test/coordinator-scope-regression.test.js` (18 tests), `backend/test/scope-mapping-drift.test.js` (4), `backend/test/coordinator-integration.test.js` (24), `frontend/test/coordinator-component-regression.test.ts` (15), `frontend/test/auth-normalization.test.ts` (6), plus the loader shims `frontend/test/ts-extension-loader.mjs` and `register-ts-loader.mjs` that let Node execute the TypeScript sources directly.

## 3. Security invariants — enforcement confirmed

An unknown or null coordinator scope denies rather than defaulting to CWTS. `getCurrentCoordinator` returns 403 when `COORDINATOR_SCOPE_TYPES[coordinator.scope]` is undefined (`nstp.authorization.js:51-52`) and again when the scope's components are not all configured (`:54`). On the client, `toCoordinatorScope` returns `undefined` for anything outside the three programs and `useCoordinatorScope` surfaces an explicit unavailable state that blocks the coordinator screens. Twelve unresolved payload variants are asserted to produce no scope, and never CWTS, in `auth-normalization.test.ts`.

An empty authorised component list means no access, never unrestricted. Enforced at `nstp.service.js:194` (`outsideForcedScope` — `[].includes(x)` is false, so everything is outside an empty allow-list), `:260`, `:340` and `:494`, and at `grades.service.js:255`. `resolveModuleComponent` now denies on presence rather than on length, which was the last place the empty case widened. Tests 7, 7c, 7d and 7e cover the read and all three write paths.

Administrator unrestricted behaviour is explicit, not implicit. The admin controllers pass no forced scope at all, so `forcedComponentScope` is `undefined` — the only value that means unrestricted — and test 8b asserts an admin write with no narrowing still creates a common module and edits a scoped one.

Coordinator endpoints scope inside the database query. All 17 coordinator routes carry `getCurrentCoordinator` (`nstp.routes.js:89-99`, `staff.routes.js:19` spread across `:27-31`, `grades.routes.js:31`), and each service call receives the server-derived component list rather than a client parameter. No coordinator-reachable call site targets an `/nstp/admin/*` path: `services/api.ts` is admin-only, `nstpData.ts` self-gates at `syncAllFromApi`, the admin assessment functions are behind `role === 'admin'` in `AssessmentManager.tsx`, the admin grade functions behind the same check in `ReportsPage.tsx`, and coordinators never render `GradesPage` or `RoleDashboardHome`.

Invalid component input produces a validation error, never CWTS. `validateStudentImportRows` rejects the batch and names the row; `requireComponentType` rejects unknown types server-side with "is not a recognised NSTP component"; and the admin import handler returns before `persistStudents`, with the message "Import cancelled — no records were saved". Tests 1-6 and 6b cover this behaviourally.

The frontend is never the authorization authority. Every coordinator read is scoped server-side; the client's scope map is documented as display-only; and `services/coordinator.ts` contains no filtering that could select records, which the regression test enforces by inspecting every `.filter(` call in the file.

## 4. Test results

Backend, `node --test "test/*.test.js"`: **132 tests, 123 passed, 0 application failures, 9 environment failures.** All nine `not ok` entries are file-level, accompanied by eleven occurrences of `PrismaClientInitializationError: Query Engine for runtime "debian-openssl-3.0.x" … generated for "windows"`; there are zero failing named subtests. The affected files are `assessment-lifecycle`, `authorization`, `h3-h4-security`, `module-lifecycle`, `module-url-security`, `profile-templates`, `seed-admin`, `semester-grades` and `staff-scope`. They exercise the same guards from a different angle and are expected to pass on the Windows host, where the generated engine matches; `prisma generate` was deliberately not run, since regenerating for Linux would break `npm run dev` locally.

The three coordinator suites run clean in this environment: **46 tests, 46 passed, 0 failed** (`coordinator-scope-regression` 18/18, `scope-mapping-drift` 4/4, `coordinator-integration` 24/24).

Frontend, `node --import ./test/register-ts-loader.mjs --test "test/*.test.ts"`: **21 tests, 21 passed, 0 failed** (`coordinator-component-regression` 15, `auth-normalization` 6).

`npx tsc --noEmit`: **exit 0** — required regression test 20, re-verified after every edit including the last. `npm run backend:lint`: exit 0.

`npx vitest run`: **environment failure**, `Cannot find module @rollup/rollup-linux-x64-gnu`. The **12 files** in `frontend/src/__tests__/` are therefore recorded as **not executed**, not as passing. That is why the coordinator assertions that mattered were reimplemented against the plain Node runner: `auth-normalization.test.ts` executes the real `normalizeAuthenticatedUser` rather than inspecting it as source.

All twenty required regression tests exist and all twenty executed. Nine of them are behavioural on the client (1-6 and the scope-vocabulary test), eleven run against the real backend service functions, and four (12, 13, 18, 19) are source-structure guards — labelled as such in the file, because "a coordinator code path never calls an admin snapshot loader" is a property of the control flow, and asserting it on the source is what stops the shape growing back.

## 6. Remaining issues

None of the following is fail-open; they are inconsistencies, dead code and environment limits.

Two backend hardenings were identified and deliberately deferred because both would require editing `backend/test/authorization.test.js`, which cannot be executed here. The status gate at `nstp.authorization.js:32` reads `coordinator.user?.status && coordinator.user.status !== 'ACTIVE'`, so a null status would short-circuit past the ACTIVE check; this is inert because `prisma/schema.prisma:112` declares `status AccountStatus @default(ACTIVE)` and the column is non-null. And the legacy single-component branch could derive real `allowedComponentTypes` with one extra lookup. Changing either would break a test that stubs a minimal coordinator row, and I was not willing to modify a suite I cannot run.

Legacy coordinators — rows with `scope = null` but a `componentId` — can list their facilitators but receive 403 on every facilitator write, because `requireAllowedComponent` needs a scope. This is inconsistent but fails closed; the fix is a data migration that sets `scope` on those rows.

`services/coordinator.ts:181` passes the training-group component label through verbatim with a cast. This is deliberate and documented: `TrainingGroup.component` is a free-text column that legitimately holds enum spellings such as `MTS_NAVY`, which the strict validator rejects, so validating here would blank legitimate rows. The row is already restricted to the coordinator's components by the query, and the value is display-only.

Component-scoped snapshot writes remain in `AssessmentsPage.tsx`, `ModulesPage.tsx`, `AssessmentManager.tsx`, `FacilitatorDashboard.tsx` and `ProgressTracker.tsx` for student and facilitator sessions. Those are unchanged on purpose: for those roles the snapshot is populated from endpoints their own role is entitled to, and the coordinator branch skips it.

Dead code worth removing on a future pass: the staff branches of `renderSection` in `App.tsx` (roughly `:1108-1132`) and the announcements bell are unreachable; `PendingAssignment.tsx:24,31` polls localStorage for state the server owns; `FacilitatorDashboard.tsx:131` and `AdminDashboard.tsx:994` read snapshot keys nothing writes; and `saveAssessments`, `saveModules` and `saveTrainingGroups` are exported but unused.

Two toolchain notes. `frontend/test/` sits outside `tsconfig.json`'s `include: ["src"]`, so those files are not type-checked — they are executed instead, which is the stronger check, but a syntax-level regression there would not be caught by `tsc`. And `frontend/test/*.test.ts` needs Node ≥ 22.18 for native TypeScript execution.

On production readiness: no security-sensitive coordinator path traced in this pass remains fail-open, and the one latent fail-open that did exist is closed and covered by executed tests. That said, twenty-one test files (nine backend, twelve frontend) could not be executed in this Linux sandbox for platform reasons, so the sign-off is conditional on running the full suite once on the Windows host — `npm --workspace backend test` and `npx vitest run` — before deploying.
